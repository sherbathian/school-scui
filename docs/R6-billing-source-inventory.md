# R6 follow-up · Billing source inventory

The current dashboard measures legacy collections only. The student profile displays legacy invoices alongside v4 monthly charges and shows imported snapshots separately. A family receipt can record cash without changing either student's balance. Reconcile these sources independently before linking records or changing a report.

## Write and import paths

| Path and source | Confirmed behaviour |
| --- | --- |
| Legacy fee items and invoices · `LegacyFeeTypeController::store/update/destroy`, `FeeInvoiceController::store/destroy`, `FeeManagement.jsx` | Legacy types are branch and academic-year specific. Invoice creation resolves the type and student within the same branch and requires enrollment for that year. The CSV UI matches an eligible student by admission number and an active fee item by title. Historical import can supply a two-decimal amount. Void changes the invoice status only when the endpoint sees no payments. |
| Legacy payments · `FeeInvoiceController::recordPayment`, `FeeManagement.jsx::importPayment` | The payment transaction locks the branch invoice, checks remaining balance and records the operator. CSV matches an invoice ID or the admission-number and fee-item pair in the selected year. CSV requires a reference and rejects reuse on the same invoice case-insensitively. Ordinary payment submissions may omit the reference and have no replay key. The reviewed void action does not take the same invoice lock, so payment/void interleaving needs a synthetic concurrency check before cutover. |
| V4 setup and monthly charges · `FeeTypeController`, `FeeGroupController`, `FeeDiscountController`, `FeeMasterController::assignStudents`, `FeeSetup.jsx` | Setup forms and CSV use the branch CRUD endpoints. Groups sync grades transactionally. Assignment uses active enrollment, current session and eligible grades, then snapshots master amount and due date into a charge. Assigning the same master/student/month does not create a second charge. The reviewed assignment does not apply a student discount or create an invoice. |
| Family receipts · `FamilyFeeReceiptController::store` | Stores submitted totals and source keys, optionally linking a guardian by their source parent ID within the branch. No verified allocation, payment or balance recalculation in this handler. Repository scope did not establish every external or command-line importer. |
| Legacy snapshots · `StudentController::show`, `LegacyStudentFeeSnapshot` | The student detail reader exposes permitted monthly snapshot values. The reviewed entry points contain no snapshot writer. Source provenance columns exist and must be preserved in reconciliation. |
| Expenses · `ExpenseController::store/update/destroy`, `ExpenseManagement.jsx::importExpense` | Create, edit and delete are branch-scoped. CSV creates through the same endpoint. Attachments are stored on create, replaced on edit and removed on delete. Attachment storage mutations are separate from SQL writes. The flow has no audited ledger posting or reversal. |
| CSV runner · `DataTools.jsx` | The finance row handlers use sequential calls. A failed row can coexist with earlier committed rows. Resume by source key and reconcile accepted rows rather than replaying an entire batch blindly. |

## Database guarantees

These are migration-defined constraints. The review did not inspect a deployed schema. None of the reviewed tables defines a per-record currency column. The dashboard labels legacy collections PKR. Confirm denomination before interpreting historical amounts or combining branches.

| Tables | Precision and keys | Ownership and deletion |
| --- | --- | --- |
| `legacy_fee_types`, `fee_invoices` | Amounts are unsigned BIGINT minor units. Type unique on branch/title/year. Invoice unique on branch/student/type/year, even after void. | Invoice references student and legacy type through composite branch keys. Student deletion cascades invoices; deletion of the referenced type is restricted. The setup migration renames the original fee type table. |
| `fee_payments` | Unsigned BIGINT minor units, branch/date index. Reference nullable and no unique replay constraint in the reviewed migration. | Composite branch/invoice FK cascades on invoice deletion. Recorder deletion nulls the actor ID. |
| `fee_types`, `fee_discounts`, `fee_groups`, `fee_group_grade` | Catalogues unique on branch/title. Discount value DECIMAL(10,2), with nonnegative and percentage caps enforced by MySQL checks or SQLite triggers. Pivot primary key is group/grade. | Fee catalogues restrict branch deletion. Pivot composite keys bind branch/group/grade; group deletion cascades and grade deletion is restricted. |
| `fee_masters`, `student_fee_charges` | Master and charge amount DECIMAL(12,2), fine DECIMAL(10,2). Master unique per group/type/session/month. Charge unique per master/student/month. | Master has restrictive composite group, type and session FKs. Charges have restrictive composite master and session FKs and a cascading composite student FK. These keys enforce branch matching; the assignment method enforces current session and enrollment. |
| `student_fee_discounts` | Dated references to a rule with optional session, no unique student/rule/period constraint in the reviewed definition. | Composite branch keys for student, discount and optional session. Student or rule deletion cascades; session deletion is restricted. No reviewed writer applies the amount to a charge. |
| `family_fee_receipts`, `legacy_student_fee_snapshots` | Nullable DECIMAL(12,2) amounts. Family receipt unique by branch/number and branch/source key when present. Snapshot unique by branch/student/month. | Receipts optionally reference a same-branch guardian with restricted deletion. Snapshots reference a same-branch student with cascading deletion. Both cascade on branch deletion. |
| `expenses`, `expense_heads` | Expense amount DECIMAL(12,2). Expense invoice number unique per branch when present, and head title unique per branch. Branch/date index. | Composite branch/head link restricts head deletion while referenced. Both tables cascade on branch deletion. |

## Balance and report readers

- `FeeInvoiceController::index/invoiceData` returns the requested eligible academic year for one branch. Payments are returned in date/ID order. Balance is amount less recorded payments, floored at zero, and status precedence is void, paid, partial, overdue, open. A void row can still carry a numeric balance; exclude it from collectible totals.
- `StudentController::feeHistory` combines each student's legacy invoices with monthly charge rows. For a monthly charge marked paid, the response shows the full amount paid; otherwise it shows full balance and no payment entries. The response derives the displayed academic year from the charge session. `StudentRoster.jsx` displays historical snapshot totals separately. These views are insufficient evidence to add both kinds of balance together.
- `AdminDashboardController::__invoke/unpaidInvoices` counts branch invoices with stored status open and positive balance, with no academic-year filter; the student count additionally limits student ID. The monthly collected card sums all branch `fee_payments.amount_cents` where paid date is at least the current month start and before the next month start. There is no invoice-status join. The expenses card counts expense records in the same half-open date window. Finance card visibility depends on module and permissions.
- `ExpenseController::index` supports a branch-local inclusive date range and search. `ExpenseManagement.jsx` also filters the loaded records and sums the displayed list using JavaScript numeric values. Treat that display total as a convenience, with exact decimal totals calculated independently for reconciliation.
- `AdminReportController::__invoke` exposes attendance, student and staff catalogues. Its report routes contain no dedicated collections, outstanding receivables, expense totals, family allocation, reversal or finance audit report. Provider internals, other dashboard widget services and any out-of-scope import commands remain unverified. The controller's organisation comparison is for its existing report catalogues.

## Proposed first implementation · R6-A reconciliation preview

Build a read-only Artisan command for an explicitly selected branch and as-of date on an isolated database copy. Report separate, deterministically ordered counts and amounts for legacy invoices and dated payments, monthly charges, family receipts, snapshots and expenses. State the date basis per source, separate void balances and flag raw overpayments, payments on voids, and receipts without allocation evidence. Label denomination unverified unless supplied from an approved source. Show snapshot periods without summing cumulative balances across months. Acceptance data must include overlapping receipt/payment amounts so the preview proves it never produces a combined cash total.

**Proposed Read.** This inventory, the R6 assessment, `backend/bootstrap/app.php`, `backend/routes/console.php`, the six finance models listed in the inventory brief and the source migrations referenced above. Read only finance definitions.

**Proposed Touch.** New `backend/app/Console/Commands/PreviewBillingReconciliation.php`, new `backend/app/Services/BillingReconciliationPreview.php`, new `backend/tests/Feature/BillingReconciliationPreviewTest.php`, `docs/PROGRESS.md`, and `docs/DECISIONS.md` for approved decisions. Command registration must be confirmed from bootstrap before any extra file is changed.

**Acceptance.** Test mixed branches, exact minor-unit arithmetic, payment date boundaries and void status, null and unmatched receipts, snapshot period handling, repeated identical runs, invalid branch and date inputs, and zero database writes. Define the invoice existence cutoff precisely and label current status if historical status is unavailable. Use synthetic fixtures on SQLite and MySQL CI. The command must emit no contact data, raw CSV payloads or attachments.

**Deployment and rollback.** First run on a disposable copy only. Capture per-source amounts and count against independent control queries, accounting for every difference. No backfill or change of dashboard or posting paths. Deployment is removable without data rollback. Actual cutover requires separate approval, mapping evidence, and zero unexplained variance. Finance posting, reversals and audit events remain for later implementation.
