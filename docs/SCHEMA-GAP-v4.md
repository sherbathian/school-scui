# Schoolhouse schema gaps against Database Plan v4

**Baseline:** `m2/sync-current-baseline` at `fcce7aa`.

**Sources:** [Database Plan v4](Schoolhouse-Database-Plan-v4.xlsx), **Columns** and **Relationships** sheets, and the ordered Laravel migrations in `backend/database/migrations/`. Workbook row numbers below refer to the current tracked copy.

This is a static schema audit. “Current” means declared by the migrations' `up()` paths. The report identifies shapes the constraints could permit. It does not assert that mismatched rows exist in MySQL. It reuses the [earlier MySQL audit](Schoolhouse-MySQL-Schema-Audit.md) for legacy fee dependencies and the difference between the inherited and target fee models. No application code, migration, database, or test suite was changed or run for this review.

## 1. Specific gaps, highest integrity risk first

### P0 · Existing relationships permit cross-branch links

| ID | Current migration evidence | Target gap and effect |
| --- | --- | --- |
| B1 · Student lifecycle events | `2026_11_12_180600` gives `student_lifecycle_events.school_id` and `student_id` separate foreign keys. The date index starts with `student_id`. | Relationships row 129 requires **`(school_id, student_id) → students(school_id, id)`**, cascading on student deletion. The parent key exists. A branch A event can currently reference a branch B student. Add a child index starting with `(school_id, student_id)`. |
| B2 · Admissions inquiries | `2026_11_12_180500` creates nullable ID-only foreign keys for `requested_grade_id` and `student_id` with `SET NULL`. | Rows 126–127 require same-branch grade and student references. The parent `(school_id, id)` keys already exist. Add child indexes `(school_id, requested_grade_id)` and `(school_id, student_id)`. An inquiry holding a family's contact details can currently point at another branch's grade or student. |
| B3 · Fee group grade assignment | `2026_11_11_074000` creates `fee_group_grade` with PK `(fee_group_id, grade_id)` and two ID-only foreign keys. The pivot has no `school_id`. | Rows 35–37 require `school_id → schools.id` plus `(school_id, fee_group_id) → fee_groups(school_id, id)` and `(school_id, grade_id) → grades(school_id, id)`. Both parent composite keys exist. Add the two branch-first child indexes and keep the existing pair uniqueness. Without the shared branch, another branch's grades can be included in a fee group's assignment population. |
| B4 · Student fee charges | `2026_11_11_080000` scopes the student via `(school_id, student_id)`, but uses ID-only FKs for `fee_master_id` and `school_session_id`. `fee_masters` has no unique `(school_id, id)`. | Rows 117–119 require branch-scoped master, session, and student FKs. Add the missing master parent key and child indexes `(school_id, fee_master_id)` and `(school_id, school_session_id)`. A branch A charge can currently take pricing or a session from branch B. The workbook checks branch equality. To enforce that a charge's session is also the session of its fee master, add a master parent key `(school_id, school_session_id, id)` and a matching child FK, or settle that invariant explicitly before implementation. |
| B5 · Expense categories | `2026_11_12_172800` uses an ID-only `expense_head_id` FK and a separate `school_id` FK. `expense_heads` has unique `(school_id, title)`. | Row 33 requires `(school_id, expense_head_id) → expense_heads(school_id, id)` with restricted deletion. Add the parent unique key and child index. Expenses can otherwise be assigned to another branch's account category and enter the wrong category totals. |
| B6 · Staff leave balances | `2026_11_11_071000` uses ID-only links to staff, leave type, and academic session, and unique `(staff_id, leave_type_id, school_session_id)`. | **The workbook also specifies these ID-only links** in rows 112–114. This is a gap in the branch invariant beyond explicit v4 parity. Propose `school_id` on balances, derived from staff, plus three `(school_id, …)` FKs to `staff`, `leave_types`, and `school_sessions`. Their parent unique pairs exist. Keep the triple unique constraint. A branch A staff balance can currently use branch B leave policy or session. |
| B7 · Role assignments and team IDs | `2026_11_13_103819` adds team keys and makes team ID part of the role and permission pivot PKs. `model_has_roles.role_id` references only `roles.id`. Team ID 0 represents global scope in `2026_11_13_103928`, while global roles have a nullable `roles.team_id`. | **Hardening beyond v4 Relationships rows 61–62.** A direct role-pivot write can pair a branch A team with a branch B role. Scoped unique role names do not prove role/team agreement. The existing global sentinel makes a naive team FK or nullable composite unsafe. Design a matching non-null role scope key and enforce role/scope pairing separately from polymorphic actor membership. Treat global and branch assignments explicitly and preserve the bounded global path. |

### P1 · Money, branch ownership, and pending relationship changes

| ID | Current migration evidence | Target gap and effect |
| --- | --- | --- |
| F1 · Monthly invoices and payments | `2026_11_11_061656` uses an invoice per student, fee type, and academic year, with integer cents. The later fee catalogue migration renames the existing fee type table to `legacy_fee_types`. `2026_11_11_061657` stores payments as integer cents. | Columns rows 730–747 and 760–770 require `fee_invoices.invoice_no`, `school_session_id`, `billing_month`, `subtotal`, `discount_total`, `fine_total`, `total_amount`, `paid_total`, and `fee_payments.amount` and `payment_method`. Add `(school_id, school_session_id) → school_sessions(school_id, id)` (row 39), invoice-number and student/month uniqueness per branch. The migrated legacy type link, the invoice-to-student pair, and the payment-to-invoice pair are already branch-scoped (rows 40 and 46). Replacing them with ID-only links would weaken isolation. The legacy invoice grain may produce several source invoices for one student/month, so the new unique key needs a reconciliation and mapping step first. |
| F2 · Charge-to-invoice link | The charge migration has neither `fee_invoice_id` nor `discount_amount`. | Columns rows 788–789 and Relationships row 116 add the nullable invoice link and discount amount. Add an indexed branch-scoped invoice FK using the existing parent key. For stronger integrity, require the invoice to match the charge's student and billing month too, using an appropriate unique parent tuple. Otherwise a charge could affect the wrong student within the same branch. Preserve a charge when clearing its invoice link. |
| F3 · Student fee discounts | No migration creates `student_fee_discounts`. `students`, `fee_discounts`, and `school_sessions` already have scoped parent keys. | Add the table with `school_id`, `student_id`, `fee_discount_id`, nullable `school_session_id`, dates and note (Columns 790–799). Add the direct branch FK and the three composite child FKs (rows 120–123). This prevents a branch A student's charges from using a branch B discount or session. Confirm the intended overlap rule for discount periods before introducing business uniqueness. |
| F4 · Legacy finance dependencies | `family_fee_receipts` and `legacy_student_fee_snapshots` sit outside v4's target table list. `2026_11_13_124344` and `2026_11_13_124345` already use a same-branch guardian or student FK respectively. | Preserve those links and retain source-to-target reconciliation until the fee cutover is proven. Audit dependants on legacy fee types, IDs and financial snapshots before any contraction. Matching cents to decimal rupees by exact arithmetic protects payment history. The audit found no missing payment-to-invoice branch key. |
| O1 · Branch identifiers and designated contacts | `2026_11_19_064652` adds `schools.group_id`, an organisation FK with default restrict behaviour, and `is_main_branch`. `school_user` already has its composite membership PK. | Columns rows 52–54 require nullable `branch_code` with unique `(group_id, branch_code)`. Without it, two branches of the same organisation can share the code used to select the intended branch. Add `school_user.is_primary_contact` (Columns rows 5–11), default false. Ask whether multiple primary contacts are allowed before adding a uniqueness rule. Relationships row 104 says `SET NULL` for the group FK, but deleting an active organisation can sever ownership. Agree on lifecycle policy before replacing restrict semantics. |
| O2 · Organisation billing and entitlement | `school_modules` already has a branch/module PK and foreign keys. Organisation subscription, plan, and billing relationships in rows 66–68, 98–99, and 141–151 do not exist in migrations. | Stage plans and subscriptions with organisation, plan, module, invoice and recorder FKs as specified. For a branch add-on, v4 lists the invoice and branch links independently. **Proposed hardening:** an invoice line that specifies a branch must agree with its invoice's `school_group_id` using shared composite parent keys or an equivalent DB-enforced association. Otherwise a branch belonging to organisation B can be billed on organisation A's invoice. Enforce unique invoice number and unique `(school_subscription_id, limit_key)`. Confirm billing and retention rules before adding cascade or nulling paths. |

### P2 · Pending directory and branch-scoped links

| ID | Gap | Effect or decision |
| --- | --- | --- |
| D1 · Lead conversion | `listing_leads` and `student_inquiries.listing_lead_id` are absent. Rows 58–60 and 124–127 specify links in both directions, each scoped by branch. | Add parent unique keys `(school_id, id)` on both tables. Prefer one authoritative conversion link with uniqueness if conversion is one-to-one. If both links are retained, use a second migration after both parents exist, and enforce reciprocal consistency. Otherwise one branch could convert another's lead or expose parent contact data. |
| D2 · Transfers | `student_transfers` is absent. Rows 130–134 specify two branch FKs, a same-branch student FK for each endpoint, and an optional recorder. | Add separately named `(from_school_id, from_student_id)` and `(to_school_id, to_student_id)` child FKs to `students(school_id, id)`. A transfer intentionally links two branches, so scoping both endpoints is essential. If only inter-branch transfers are allowed, decide whether to add a check requiring different branches. |
| D3 · City and area agreement | `2026_11_18_154808` gives schools separate nullable city and area FKs. Areas are unique by `(city_id, slug)`, with an ID-only city FK. | Rows 5 and 102–103 specify `CASCADE` for areas under a city and `SET NULL` for a school's optional area. The migrations currently restrict both deletions. The workbook's ID-only links also allow a school to pair a city with an area in a different city. If preserving paired location integrity at DB level, add a unique `areas(city_id, id)`, a matching composite FK, and enforce that an area implies a city. Agree on deletion behaviour before changing the admin's protection for in-use locations. Apply the same agreement to future courses and books that carry both IDs. |
| D4 · New branch resources | Relationships rows 69, 78–89, 93–97, and 138 describe independent branch links for programmes, listing taxonomy pivots, listing fees/media, pages, site settings, stats and study resources. These links are pending. | Put a branch FK on each applicable row when introducing the feature. Use composite PKs for the three taxonomy pivots and scope programme and page slugs to `(school_id, slug)`. Add the second FK to each pivot's global taxonomy catalogue. An index alone cannot prevent an orphan branch or a dangling taxonomy link. Keep branch ID nullable only where the workbook specifies a shared/public resource. |

**MySQL delete-rule constraint.** MySQL `ON DELETE SET NULL` on a composite FK nulls **every child column** in that FK. It cannot be used directly with a non-null owning `school_id` in B2, F2 or D1. Prefer a composite `RESTRICT` FK plus explicit, transactional unlink-before-delete, or add a separate nullable owner/reference pair with a check that requires both values to be present together and to match the owning branch when present. Choose and test one design before migration. With nullable component columns, a composite key alone can skip validation when any component is null.

**Access and audit actors.** A user may legitimately act as a platform admin or work across branches. Keep global user FKs for recorder, reviewer, and uploader columns where v4 specifies them. Verify authority at write time and retain the actor for audit. A blanket FK from historical audit rows to current branch membership could erase or obstruct valid history when a user changes roles.

## 2. Proposed migration order and verification tests

Each row is a proposed increment. Use synthetic fixtures on a disposable MySQL database. Test actual DB inserts or updates using the query builder as well as relevant HTTP entry points. For every scoped FK, assert the valid row persists, the mismatched attempt fails with an integrity error, and the prior values remain intact. Use savepoints or isolated requests where needed to inspect the surviving records after a rejected statement.

| Sequence | Proposed migration | Concrete verification |
| --- | --- | --- |
| 0 | **Preflight and additive parent keys.** Check for cross-branch links, unresolved references and duplicates. Report invalid row IDs and stop the migration if ambiguous. Add named unique parent pairs for `expense_heads` and `fee_masters`, and later pairs only when required. Preserve MySQL type/signedness and index column order. | Seed a valid pair and a mismatched charge and expense. Verify the preflight flags the offending IDs and the data is unchanged. Repair only through an explicit mapping, rerun, and verify the scoped parent indexes exist. |
| 1 | **Lifecycle events and expenses (B1, B5).** Add branch-first child indexes and composite FKs, then retire the old ID-only FKs. Keep the existing ownership and deletion semantics. | Branch A can write an event for A's student and an expense for A's head. Substitute B's student or expense head independently and expect rejection. Verify student deletion cascades its events and expense-head deletion is restricted while used. |
| 2 | **Admissions (B2).** Switch application writes to the chosen branch-scoped optional-link design, then install its constraints and retire ID-only FKs. | Store an inquiry linked to A's student and grade. Try B's student and B's grade separately and expect rejection. Verify an unconverted inquiry is valid and the supported unlink/delete path leaves the inquiry and its `school_id` intact. |
| 3 | **Fee group grade pivot (B3).** Add nullable `school_id`, update pivot writers to include branch, and backfill only when both parents agree. Enforce non-null and add composite FKs before dropping old links. | Sync an A group to A grades through the normal API and verify the pivot stores A. Attempt direct writes crossing either parent to B. Verify duplicate assignment still fails and deleting a used grade follows the restrictive rule. |
| 4 | **Charges and leave balances (B4, B6).** Add scoped master/session charge links and leave balance ownership. Update leave balance writers before enforcing a non-null owner. Replace single-column FKs after validating backfill results. | Create an A charge with A student/master/session, then try a B master and B session independently. If enforcing master/session equality, also try different sessions within A. Create an A leave balance and reject changing its staff, leave type or session to B. |
| 5 | **Role scope integrity (B7).** Design and backfill an explicit global/branch scope key before adding role/scope pairing. Add constraints in a separate migration after confirming existing package operations. | Assign A's role in A and the global platform role in global scope. Directly pair B's role with A's team and try assigning a global platform role in a branch scope. Expect rejection, while legitimate login and branch authorisation still succeed. |
| 6 | **Add monthly billing columns and discount records (F1, F3).** Add nullable invoice keys and amounts, the scoped session FK, and payment amount/method. Add the discount table with scoped FKs. Keep the legacy writer usable during transition. | Record an A monthly invoice with A's session and student. Reject substitutions from B. Record a payment against A's invoice and reject B's invoice. For discounts, independently substitute B's student, discount, and session. Verify an allowed null session works. |
| 7 | **Backfill and cut over fee history (F1, F2, F4).** Reconcile old invoices, receipts and payment allocations to the monthly grain. Add charge invoice links and uniqueness only after deduplication. Require the new keys when all writers and reads have switched. Remove legacy columns/tables in a separate release after reconciliation. | Seed two old fee-item invoices for the same student/month plus partial payments and a receipt. Verify totals and payment provenance after consolidation. Assert duplicate branch invoice number and duplicate student/month invoices fail while the same invoice number in another branch succeeds. Assert charges reject another branch's invoice and, if enforced, another student's invoice in A. |
| 8 | **Organisation identifiers and billing (O1, O2).** Add branch codes and the contact marker. Create catalogue and plan tables before subscriptions, then invoices before lines and payments. Add DB enforcement of invoice/branch organisation agreement. | Use the same branch code in groups A and B, reject a duplicate in A. Assign valid primary contact data without granting additional rights. Bill A's branch on A's invoice, reject B's branch, and accept a valid organisation-wide line with no branch. Reject duplicate invoice numbers and duplicate per-subscription limit keys. |
| 9 | **Lead conversion, transfers, and locality (D1–D3).** Create leads before adding any inbound inquiry link. Add scoped transfer endpoints against existing students. Schedule geography constraints and any delete-rule changes once the unlink behaviour is agreed. | Link an A lead to an A inquiry, reject a B inquiry, and verify unlink preserves the lead owner. Transfer from A/student A to B/student B, then swap either student ID and expect rejection. Accept the proper area/city combination, reject a mismatched one, and test the agreed deletion policy. |
| 10 | **Feature-specific branch resources (D4).** Create global taxonomy parents first. Add scoped content, media, site, stats and mapping-table keys with each feature. | For each taxonomy pivot, attach a valid pair, reject a missing branch and missing vocab ID, and reject a duplicate pair. For programmes and pages, allow a slug in two branches but reject a duplicate in the same branch. For other branch-owned resources, reject an unmatched branch ID and preserve valid optional global rows where allowed. |

For the data migration, keep reconciliation totals by branch and period and require a documented exception for missing sessions or ambiguous legacy amounts. Never infer a branch by overwriting one parent's ownership to match a conflicting record. Keep production-engine confirmation and backup/restore evidence as separate deployment prerequisites.
